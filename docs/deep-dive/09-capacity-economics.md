# 容量与经济性：从负载分布到总成本

本章所有数字是合成参数，不代表任何公司实际用户、预算或采购计划。价格使用归一化的虚构成本单位，未引用供应商现价。脚本复算算术，不做负载测试。

## 1. 至少拆开七个量

注册账号、MAU、DAU、用户轮数、记忆服务请求、主模型调用、后台/子任务调用分别计量。服务请求次数也不等于SQL数或模型数。

假设1,000万注册账号中有10万DAU，每天每人8轮，记忆服务每轮1.25次、主调用每轮1.1次、峰均比10、平均模型占用6秒：

| 结果 | 算法 | 合成结果 |
|---|---|---:|
| 用户轮/日 | 100,000×8 | 800,000 |
| 记忆服务峰值请求/秒 | 800,000×1.25÷86,400×10 | 115.74 |
| 主模型在途并发 | 800,000×1.1÷86,400×10×6 | 611.11 |

占用秒数需包括真实发送、思考、工具续跑、失败和取消影响；不能把供应商可供并发当已确定。测试短时突发、N-1和重度账号，不能从一个小请求线性推断目标规模。

## 2. 从可见条目到物理字节

用户可见一条记忆，底层可能有多Claim、Evidence、来源片段、修订和依赖边。应测每可见有效条目的分摊字节，并保留对象数、边数、正文共享和p50/p95/p99。

```text
逻辑量 = Σ各对象当前行数×实测平均行宽 + 受管正文 + 依赖边
物理规划 = 逻辑量 + 各类索引 + 实测历史 + 在线副本 + 实际备份
          + WAL/重建/迁移双份/失败队列/临时导出/余量
```

合成例子中50万记忆账号、平均40条、每条5KB，当前逻辑量100GB。历史倍率1.5、普通索引附加70%、3在线+1备份等价值产生约1.02TB。倍率只是敏感性模型，实际备份压缩和增量不应长期用等价值代替。

把每条分摊字节从5KB改成10KB，上述相关空间约翻倍，但不意味着最终模型输入也必须翻倍；检索/装配应有独立预算。反过来，输入固定也不意味着DB查询和索引维护成本固定。

## 3. 三类成本不要相互冒领

| 优化 | 可能减少 | 不能直接声称 |
|---|---|---|
| 装配缓存 | DB读取、解析、CPU、内部重复渲染 | 模型输入或账单一定变少 |
| 内部ContextDelta | 宿主/worker传输与重建 | 模型只接收delta |
| 供应商前缀缓存 | 真命中时对应输入收费 | 任意相似可命中、所有成本下降 |

完整wire包含当前输入、系统/开发指令、工具Schema/结果、历史/接续与媒体。预览和真实发送不同，局部token省得再多也不能作为完整费用证据。

## 4. 一个可以复算的归一化费用模型

[输入参数](../../examples/cost-scenario.json)设每月30天、同上DAU/轮数/主调用系数：60%主调用注入900记忆token，每用户轮平均增加40个结构化输出token，2%轮次额外一次800输入/100输出记忆调用。

虚构单价为每百万未缓存输入1单位、缓存输入0.25单位、输出4单位。它们只用于比较方向，没有对应货币或供应商。

```bash
python3 tools/cost_sensitivity.py
```

| 单项改变，其他参数固定 | 记忆增量/月 | 相对基线变化 |
|---|---:|---:|
| 基线 | 18,672.0 | 0 |
| 每次记忆输入多500token | 26,592.0 | +7,920.0 |
| 平均结构化输出从40增到300token/轮 | 43,632.0 | +24,960.0 |
| 额外记忆调用从2%增到10%轮次 | 20,976.0 | +2,304.0 |
| 仅记忆输入30%真实缓存命中 | 15,464.4 | −3,207.6 |

主回答基线另算：示例每主调用2,000输入/512输出，月度基线106,867.2单位，未假设主回答缓存。基线加记忆增量为125,539.2单位。额外调用与主调用分开计，不能把同一输出重复分摊。

这里未计基础设施、运维人工、对象/媒体、存储、检索、网络、真实推理收费、账单税费或供应商限流代价；不能把这个合成合计用作预算承诺。

## 5. 无条件后台工作为什么危险

用相同虚构800输入/100输出与单价，如果每天无条件为1,000万注册账号调用一次，30天约增加360,000归一化单位；这不是预测，只说明触发策略会改变数量级。

因此后台按真实变更、活跃任务和版本增量触发，无变化不重算，闲置账号不常驻LLM。候选、摘要、embedding、回填和导出都有每账号/父任务上限与公平调度。

## 6. 被低估的短寿命数据

候选区、预览/bundle、交付回执、幂等结果、Outbox、失败重试、调试和导出都可能包含正文或可重建引用。不能因为不在memory主表就忽略其容量、权限和删除。

回执尽量只保必要ID/版本/状态，正文按独立最早期限治理。无候选保留许可的本轮内容不能为方便恢复写入队列；重试不重置TTL。清理积压单列deadline，而不是在总体平均存储里消失。

## 7. 控制面是需要采购/保留资源的能力

停止/删除不能被付费额度耗尽或大批整理饿死。实际设计需要认证与防滥用、独立持久登记、优先队列、连接/并发保留和恢复重放能力。

单列停止请求QPS、意图持久化时延、阻断时延、恢复水位差、清理积压及各副本状态。业务库有三份副本不自动证明独立登记故障域。

## 8. 放量前的测量清单

按空/普通/重度账号、冷热缓存、索引追平/滞后、并发纠正删除、正常/N-1/供应商限流分组量P95/P99。记录扫描行、返回行、锁等待、连接池、预算冲突、真实usage、未知费用和账单差异。

每千轮成本与每成功故事成本同时报，避免通过减少服务覆盖或拒绝困难请求获得表面低成本。当前输入降级、未授权、未接入、控制故障和真实合法空结果都保预定义分母。
